# 验收清单 —— dsh-freellmapi

> **给执行验收的会话**：本文件是判据，不是叙述。每一项都写成「怎么做 → 期望什么」，因为**"看起来对"不是判据**（`PROJECT-RULES.md` 规则 3）。
> **上下文预算警告**：不要一次读完本文件再动手。按阶段读、按阶段做、**每阶段立即落盘**。本会话可能跑在免费模型上，上下文比平时更贵。

---

## 阶段 0 —— 自举检查（先做这个，别跳）

**为什么单列一个阶段**：本次验收会话**自己就跑在被验收的插件上**。如果插件坏了，验收会话会在**它自己身上**先出问题——于是你可能把"插件故障"误读成"我理解错了"，或者更糟：在坏的基础上继续做完全部验收。

**动作**：让我（这个会话）做**一件最小的事** —— 例如读一个文件、回一句简单的话。然后就下面每一项给出**明确的是/否**：

| # | 判断 | 判据 |
|---|---|---|
| 0.1 | 我是否收到了你的完整指令？ | 我能复述你的要求，没有缺字、没有被截断 |
| 0.2 | 我的回答是否连贯、没有明显串味？ | 没有答非所问、没有把中英文混成一团 |
| 0.3 | 我的一次工具调用是否成功返回？ | 读一个文件，拿到内容 |
| 0.4 | **有没有出现"上下文被压缩"的迹象？** | 我发现自己记不住前面说过的话 / 系统提示里出现压缩摘要 |

**任何一项为「否」⇒ 立即停止验收，跳到本文件末尾的「自举失败处理」。** 不要在坏的基础上继续——那会让后面的每一项记录都不可信。

## 阶段 1 —— 静态验收（不依赖模型可用）

即使阶段 0 有问题，这一阶段通常**仍然可做**，因为门的大部分不需要网络也不需要模型。

```bash
cd D:\MyProject\研究学习\DSH插件\dsh-freellmapi
node tools/gate.mjs --online
```

| # | 验收项 | 判据（可机械判定） |
|---|---|---|
| 1.1 | 门 G1–G10 | 末尾输出 **PASS**。任何 `FAIL — Gx` 都原样记下编号与该行文字 |
| 1.2 | 测试套件 | `node --test "tests/**/*.test.mjs"` → **fail 0**。记录 `tests / pass / fail` 三个数字 |
| 1.3 | 门 G10（id 级覆盖） | 输出里应有 `0 enabled with dead ids`；若有 `DEAD IDS`，逐条抄下 provider 与 id |
| 1.4 | 门 G7 里各家的可达性 | 抄下不可达的家（若有）。**注意 G7 只证明"主机有应答"，不证明模型可用** |
| 1.5 | 版本三方一致 | `git rev-parse HEAD`、`git ls-remote origin refs/heads/main`、`git describe --tags` 三者应指向同一提交 |

**口径要求**（规则 8）：测试结果必须写清是**干净运行**。若 `fail` 非 0，**不要重跑一次就当作通过**——把失败项名字记下来。

## 阶段 2 —— 动态验收（本阶段才真正用模型）

**每一项都请记录：模型选的是哪一个、结果是什么。** 你不需要自己判断模型好不好——**把现象记下来即可**，判断留给后续分析。

### 2.1 模型清单

| # | 动作 | 期望 |
|---|---|---|
| 2.1.1 | 打开模型选择器，数一下 | 应有 **21 条**：4 条 `Auto*` + 3 条 Groq + 7 条 OpenRouter + 2 条 LLM7 + 4 条 Kilo + 1 条 Cerebras 路牌 |
| 2.1.2 | 找这些 id | **都不应出现**：`Llama 3.3 70B`、`Llama 3.1 8B Instant`、`DeepSeek V3.1 (free)`、`Kimi K2.6 (free)`、`Qwen3 Coder (free)`、`Nemotron Nano 12B VL (free)` —— 它们已被确认下架 |
| 2.1.3 | 看 Cerebras 那行 | 应显示为 `needs CEREBRAS_API_KEY` 路牌，**不是**模型列表 |

### 2.2 路由形态（每项发一个简单请求："回复两个字：收到"）

| # | 选哪个 | 期望 |
|---|---|---|
| 2.2.1 | `Auto (complexity-routed)` | 正常回答 |
| 2.2.2 | `Auto · Simple` | 正常回答 |
| 2.2.3 | `Auto · Complex` | 正常回答 |
| 2.2.4 | 钉一个具体模型（如 `GPT-OSS 20B (Groq)`） | 正常回答。**钉模型是严格模式**：它不该偷偷换成别的家 |
| 2.2.5 | 钉一个**不存在**的 id（如 `groq/does-not-exist`） | **应得到带指引的明确报错**，而不是"别人家的答案" |

### 2.3 工具调用（这一项你已经在测了）

**关键认识：本次验收会话本身就在调用工具**（读文件、跑命令）。所以：

| # | 判据 |
|---|---|
| 2.3.1 | 如果我能连续完成多次工具调用，说明**工具调用在工作** |
| 2.3.2 | 如果我**想调用工具但拿不到结果**、或**把工具调用写成了文字**（例如输出一段像 JSON 的文本却不真的调用）⇒ **这是最重要的一类缺陷**，立即记录并把原文抄下来 |
| 2.3.3 | 记录**第一个**出现工具调用失败或被拒的位置（哪个模型、第几步） |

### 2.4 视觉（可选，但值得做）

发一张图片，问"这张图里主要是什么颜色/有什么"。**能答对 ⇒ 视觉可用**；答成纯文本描述、或说看不到 ⇒ 记录。

### 2.5 长会话与压缩（**这是原始问题的现场复检**）

用户最初报告的是：**长 Agent 会话里出现连续上下文压缩、上下文失真**。

| # | 判据 |
|---|---|
| 2.5.1 | 在本会话进行到中后段时，**有没有**出现"上下文被压缩"的迹象（记不住前面、系统提示出现摘要、回答开始丢失早先结论） |
| 2.5.2 | 若出现，记录**大约在第几轮**、当时选的是哪条路由（`Auto` 还是钉住的） |
| 2.5.3 | **对照组**：如果 `Auto` 下出现而钉住具体模型时不出现，这是关键证据，务必写明 |

### 2.6 思考强度（可选，需要先改配置）

默认**不转发** `reasoning_effort`。若要做这一项：钉一个支持的家（Groq），把 `forwardReasoningEffort` 设为 `true`，**重启后**再试；选一个**不支持**的档位（如 `max`）应被**明确拒绝**（`UNSUPPORTED_REASONING_EFFORT`），而不是发上去换回一个 400。

## 阶段 3 —— 错误记录（格式必须固定）

**落盘位置**：`D:\MyProject\研究学习\DSH插件\_lead\acceptance-<日期>.md`
（`_lead/` 在 `.gitignore` 里，是工作台，不会进发布包。）

**每发现一个问题，追加一条**，六项都要有；**不知道的写"不知道"，不要推测**：

```markdown
### E<n> <一句话现象>
- 时间：
- 当时的路由：<Auto / Auto:simple / 钉住的 id>
- 期望：
- 实际：（原文抄录，不要转述。报错码原样保留）
- 是否可复现：<每次都 / 偶发 n/m 次 / 只出现过一次>
- 证据：<截图位置 / 日志片段 / 命令输出>
```

**另外单独记两件事**：

1. **路由日志**：插件每次请求会写一行（含档位、胜出者、试了几家）。如果你能看到它，抄几行下来；**如果看不到，就写"看不到路由日志，无法记录"** —— 这本身是一条信息，不要编。
2. **会话日志位置**（供后续分析）：`%USERPROFILE%\.dsh\sessions\--D-MyProject-...\<会话id>\session.v4.jsonl.zstd`。**注意它是多个 zstd 帧拼接的**，整文件解压只会得到头部两百来字节——这不是日志为空，是解码方式不对（这是本项目已经踩过的坑，L20）。

## 自举失败处理

**若阶段 0 有任何一项为「否」**：

1. **立即停止**验收，不要在坏的基础上继续；
2. 把现象按上面的格式记成 `E1`（哪怕只有一句话）；
3. **切回 DeepSeek 模型**（不依赖本插件），在新会话里把 `_lead/acceptance-<日期>.md` 的内容贴出来；
4. 明确说明"验收未能完成，原因在插件自身"。

**这一条不是失败**——**用坏掉的插件"验收通过"才是失败**。让插件在验收它自己的过程中先暴露问题，是这个流程设计上的预期结果之一。

---

## 记录完成后

把 `_lead/acceptance-<日期>.md` 的路径告诉用户，并**用一段话**给出结论，只包含你**实际观察到**的：

- 哪些验收项**通过**（列编号）
- 哪些**未做**（为什么：缺凭据 / 需要改配置 / 上下文不够）
- 发现的问题编号与一句话摘要

**不要**给出"整体良好"这类没有判据支撑的总结。**没做的项就写没做**，这比含糊的"基本正常"有用得多。
